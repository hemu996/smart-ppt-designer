# 失效案例库

这里记录"踩过的坑"。它的价值只在被**读**的时候才存在——每次构思（工作流第 2 步）前必须先扫一遍本目录，把与本次 `relation_type`、受众或主题相近的案例当作本轮反例。

## 一、什么时候写

出现以下任一情况就在终审（第 8 步）写出一个案例文件：

- 生成出的页面**结构明显不适配**内容（例：三个竞品对比被排成双栏）；
- 用户指出问题时，问题是**可复现的规则级问题**（不是"我不喜欢这个蓝色"这类一次性偏好）；
- 同一类问题**第二次**出现（第一次可以只记在本文件末尾的"候选"里）。

## 二、文件命名

`fc-YYYYMMDD-NN.md`，例如 `fc-20261104-01.md`。一天内多个案例用 `-01`、`-02` 递增。

## 三、模板（复制后填写）

```markdown
---
id: fc-20261104-01
date: 2026-11-04
relation_type: 比较
slide_type: content
card_used: layout-two-column
audience: 竞赛评委
severity: 严重
---

## 现象

（生成了什么、错在哪里。用一句话说清，例如："三个竞品对比被排成左右双栏，中间一栏挤了 2 个对象。"）

## 场景（原简报内容特征）

（什么样的输入触发了这个错。例如："简报要求对比 3 家社区服务机构的覆盖范围、价格、响应速度。"）

## 根因

（为什么会错。例如："检索时只命中了 relation_type=比较，未检查对象数量；layout-two-column 的适用条件写了'两个平级对象'，但被当成通配。"）

## 规避方式

（下次怎么做。要写成可执行动作，例如："对象 ≥ 3 时强制改用 comparison-matrix；在 layout-two-column 的反例段补上'对象 ≥ 3 禁用'。"）

## 是否升级为卡片改动

（是/否 + 具体改动；若同类问题第二次出现，应改为"是"。）
```

## 四、写完要做的两件事

1. 如果结论是"卡片边界不清"→ 去改 `../cards/<card-id>.md` 的**适用条件/反例**段；
2. 如果是"确实缺一种结构"→ 按 `../../references/card-spec.md` 新建卡片（新增前先确认现有卡片覆盖不了）。

## 五、检索建议

`relation_type` 与 `slide_type` 决定命中优先级；`severity: 严重` 的案例必须逐条核对。案例累计超过约 30 条时，把反复出现、已被卡片吸收的案例归档到 `_archive/`，保持本目录可扫读。
